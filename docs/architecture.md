# Architecture

`drup` keeps workflow authority in Go and uses agents as coordinators and scoped executors. The agent layer may choose work, but it does not become the authority for a mutation, a validation gate, or a recovery decision.

## Runtime boundaries

```text
CLI / stdio MCP
       │
internal/app ── command and MCP composition
       │
       ├── session + audit + runstate + operation  (authority and evidence)
       ├── backup + restore                        (recovery)
       ├── inventory + report                      (baseline and outputs)
       ├── coreupgrade + contribplan + patch       (upgrade operations)
       ├── scan + envdetect + composerutil         (environment/analysis)
       └── packaging + installer                   (agent integration)
```

`cmd/drup/main.go` owns process startup and interrupts child processes on `SIGINT` or `SIGTERM`. `internal/app` owns the public command dispatch and the real MCP handlers.

## Durable project state

A project-local `.drup/` directory holds operational state. Important records include:

| Location | Role |
|---|---|
| `.drup/runs/<run-id>.json` | Versioned upgrade-run authority, phase, allowed actions, append-only evidence, checkpoint plan/history, inventories, and pending human work. |
| `.drup/operations.v1.json` | Idempotency and operation reconciliation records. |
| `.drup/audit.jsonl` | Mutation audit trail subject to configured caps. |
| `.drup/backups/<backup-id>/` | Database archive, filesystem archive, and manifest checksums. |
| `.drup/restores/` | Restore journals and preserved recovery state. |
| `.drup/config.json` | Optional project guardrail overrides. |

Run evidence stores sanitized summaries and hashes rather than raw command output. This makes an interrupted MCP session resumable without treating an agent transcript as a source of truth.

## Authority model

1. `session_open` binds the MCP process to one canonical Drupal root.
2. `run_create` creates an active, project-bound upgrade run.
3. Guarded tools check session identity, backup freshness, mutation budget, and whether the run’s current phase permits the action.
4. Checkpoint execution records bounded command-step evidence. A checkpoint commit requires independently recorded validation evidence that matches the candidate and paths.
5. A run persists its allowed actions, so restarting an MCP server does not re-derive authority from prompt text.

A `--locked` MCP server refuses all mutating calls even if other guards would allow them.

## MCP catalog as a single source of truth

`internal/mcp.ToolSpec` defines each exposed tool’s JSON schema, side-effect classification, guard policy, and stub visibility. The generator produces:

- `internal/mcp/tool-catalog.generated.json`
- the generated section of [`docs/mcp-tools.md`](mcp-tools.md)

Run `go generate ./...` after changing a ToolSpec. Run `go run ./cmd/mcp-catalog-gen --check` in CI or review to verify that committed generated bytes are current. Do not edit the generated block in `mcp-tools.md` manually.

## Agent packaging

`internal/packaging` renders the skill, role files, command prompts, and MCP registration snippets for Claude Code, OpenCode, and Codex. `internal/installer` detects the installed host, backs up drup-managed files, merges only drup’s registration, and records state in the user configuration directory. The repository templates are the source of truth; installed copies are generated outputs.
